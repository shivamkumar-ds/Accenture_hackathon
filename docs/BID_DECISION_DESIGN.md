# Bid Decision — Design Proposal (V1)

Status: **Proposed, not implemented.** No code changes accompany this document.

(Previously named "Decision Review." Renamed because users are making a
decision, not reviewing one — the button that launches this page is "Make
Business Decision," not "Review Decision.")

## 1. Product Contract

Bid Decision has exactly one job: turn an AI recommendation into a recorded
business decision. It is not a remediation tool, not an audit system, and not
a workflow engine — those are explicitly out of scope until real usage
justifies them (see §6).

**Reads (existing data, no new computation):**
- The mission's current `Recommendation` (type, risk level, confidence
  fields, executive summary) via the existing evaluation response.
- The compliance matrix and gap analysis for that mission (same source
  Reports already uses).
- Evidence sources already resolved server-side per requirement.

**Writes (exactly one thing):**
- One business decision: `proceed`, `rejected`, or `needs_revision`.
- One optional free-text note.

That's the entire contract. If a future change to this page doesn't fit
"reads existing evaluation data in, writes one decision out," it belongs in
a later version, not a revision of V1.

## 2. Entry Point

**Option A: launched from the Reports page**, via a "Make Business Decision"
button next to the existing "Download PDF Report" action on an evaluated
tender. No new sidebar item, no new top-level nav concept — Bid Decision is
a destination you arrive at after reading a report, not a place you browse
to independently.

Journey:

```
Upload Tender → AI Analysis → Report → Make Business Decision → Decision Saved
```

After saving, the user lands back on Reports/Tender Workspace, where the
mission now shows its recorded decision (and, for Proceed/Rejected, its new
Completed status — see §5).

## 3. Page Layout

Single page, split into two visually distinct zones — the divider is
deliberate: it reinforces that the AI advises and the human decides, which
is a core part of the product's philosophy, not just a layout choice.

```
========================================
 AI ANALYSIS
========================================
 Decision Summary   (recommendation, critical/high-risk counts,
                      requirements reviewed vs. met — a snapshot
                      before the detail below)
 Recommendation      (type, risk level, executive summary)
 Why                 (gaps grouped by requirement_type)
 Evidence             (inline per gap — company record + source doc)

----------------------------------------
 BUSINESS DECISION
----------------------------------------
 Proceed / Rejected / Needs Changes
 Notes (optional)
 [ Save ]
```

Section detail:

1. **Decision Summary** — a small stats box above the detailed breakdown:
   recommendation type, count of critical-risk items, count of high-risk
   items, total requirements reviewed, requirements met. All values are
   aggregates of data already on the page (compliance matrix + gap
   analysis) — no new computation, just surfaced earlier so the user isn't
   forced to scroll through every requirement to get the headline.
2. **Recommendation** — recommendation type (Proceed / Conditional Go /
   Review / No-Go), risk level, executive summary. Same data Reports
   already renders; no new fields.
3. **Why** — gap analysis entries grouped by `requirement_type`
   (Eligibility, Technical, Certification, Experience, Evaluation Criteria,
   Deadline, Submission — the categories are the real enum values, not
   invented labels like "Financial Eligibility," since the data doesn't
   actually distinguish financial eligibility from other eligibility
   criteria). Each group is collapsible, shows count, and defaults open only
   for groups containing `not_met` or `review_required` items. Each item
   shows: requirement description, status, risk level (Critical/High/Medium/
   Low, direct from `risk_level`), evidence source (company record + source
   document, when present), and the reason/notes text already generated by
   the Decision Engine.
4. **Business Decision** — a three-way choice: Proceed / Rejected / Needs
   Changes. The third option is labeled "Needs Changes" rather than "Needs
   Revision" in the UI — "revision" reads as if the tender itself needs
   rework, when really it's the company's own eligibility that needs work.
   The underlying value stays `needs_revision` in the API/database; this is
   a display-label change only, not a contract change. One optional notes
   textarea below it.
5. **Save** — a single submit action. No draft state, no autosave; the
   decision is either saved or the page hasn't changed anything.

Explicitly not present: confidence selector, approver field (derived from
the authenticated session, not entered), history timeline, task list.

## 4. API Contract

One new endpoint, no new tables:

```
PATCH /api/v1/missions/{mission_id}/decision

Request body:
{
  "decision": "proceed" | "rejected" | "needs_revision",
  "notes": string | null
}

Response: MissionRead (existing schema), reflecting the updated
actual_outcome, outcome_notes, status, and completed_at.
```

Validation: `decision` is a `Literal` at the Pydantic layer — enforced at
the API boundary even though the underlying `Mission.actual_outcome` column
stays an untyped `String` (no migration). Approver identity comes from
`get_current_user`, not from the request body.

Read side: no new endpoint. The page composes data from the evaluation
endpoint the Reports page already calls.

## 5. State Transitions

| Decision        | `actual_outcome` | `outcome_notes` | `status`             | `completed_at` |
|------------------|-------------------|-------------------|------------------------|-----------------|
| `proceed`        | `"proceed"`       | notes or null     | `completed`            | now()           |
| `rejected`       | `"rejected"`      | notes or null     | `completed`            | now()           |
| `needs_revision` | `"needs_revision"`| notes or null     | unchanged (`awaiting_approval`) | unchanged |

`completed` is an existing `MissionStatus` value that nothing in the
codebase currently transitions to — this finally gives it a real trigger,
using two fields (`completed_at`, `actual_outcome`) that already existed
but were never written. No enum change, no migration.

**Visibility:** `completed` missions (Proceed or Rejected) move out of the
active Tender Workspace/Dashboard views the same way `archived` ones already
do, but remain queryable — e.g. under a "Completed" filter — since a
rejected tender's reasoning should stay discoverable, not disappear.
Archive remains a separate, later, user-initiated action for anything the
user wants fully out of view, matching the existing soft-delete convention
elsewhere in the product. Needs Changes leaves the mission exactly where it
already was: visible, actionable, `awaiting_approval`.

## 6. Explicitly Out of Scope for V1

- Decision history / append-only audit log (`mission_decisions` table).
  Revisit only if usage shows decisions get revised more than once per
  tender in practice.
- Decision confidence scoring — no shared rubric exists for what a
  manager's "High" means; collecting it now would produce data with no
  clean interpretation.
- Fix Gaps & Reanalyse loop, auto-generated action plans, projected score
  changes.
- Task assignment / notifications / workflow automation.
- Any new database migration beyond none — this design requires zero
  schema changes.

## 7. Open Question for Product

Who should be allowed to record a Business Decision — any authenticated
company user, or a specific role (`bid_manager` / `executive`)? The
codebase already has a precedent for role-gating a sensitive action
(capability deletion is `require_administrator`-only); Bid Decision
needs its own explicit answer before the endpoint is built, since it
determines whether the route needs a role check at all.

## 8. Future Idea — Not V1, Not V2, Just a Note

Keeping "Business Decision" as its own concept (rather than folding it into
`MissionStatus`) leaves room for a later flow without redesigning anything
built here:

```
Rejected → Reopen Decision → Issue Fixed → Re-run Evaluation
```

Nothing here commits to building it. It's recorded so that if/when reruns
or a decision history become justified by real usage (see §6), this design
doesn't have to be undone to support them — the "Business Decision" concept
was already designed as separable from "Mission Status" from day one.
